# Handoff — session crash + model fixes (2026-08-25)

Two fixes found on the **HotMic install** (`~/HotMic/assistant`) that should
also be applied to the **personal install** (`~/assistant`):

1. **Upgrade the SDK** — `claude-agent-sdk` 0.1.39 → 0.1.81 (fixes sessions
   crashing mid-task)
2. **Upgrade the model** — retire the deprecated `claude-sonnet-4-20250514`

The personal install is an independent checkout with its own `context/`, its
own `.venv`, and its own gitignored config. **Neither fix travels through
git** — one is a `pip` operation, the other edits a gitignored file. Pulling
brings this document and the install template, nothing more. Use the "Apply"
section below.

Jump to: [Apply to the other install](#apply-to-the-other-install)

---

## Fix 1 — SDK upgrade (the crash)

**Symptom.** Sessions died mid-task; the UI showed a crash. Originally
reported as "crashes whenever I ask it to do anything with the browser."

**Cause — not the browser.**

```
claude_agent_sdk._errors.MessageParseError: Unknown message type: rate_limit_event
```

The bundled Claude Code CLI (2.1.240) emits a `rate_limit_event` message as a
session approaches a usage limit. The **installed SDK was 0.1.39**, which has
no case for that type, so `parse_message` fell through to
`raise MessageParseError`. That killed `_receive_loop`
(`manager/claude/session.py:653`), and the dead-session reaper then closed the
session as `subprocess_crashed`.

**Why it looked browser-specific.** Browser work is token-heavy (screenshots,
DOM snapshots), so it reaches the usage limit fastest. The crashed sessions
never wrote a JSONL at all — they died before any browser tool ran. Any
sufficiently long session would crash the same way.

**The pin was already correct.** `requirements-claude.txt` has required
`>=0.1.81,<0.2` since 2026-06-18, and its comment already documents the
relevant upstream fix ("0.1.40 made the SDK skip unknown message types").
**The venv had drifted below its own floor.** This is the key point for the
other install: `git pull` does not change an already-installed package.

**Fix.**

```sh
.venv/bin/pip install -U 'claude-agent-sdk>=0.1.81,<0.2'
```

0.1.81 parses the message into a `RateLimitEvent`, which `_process_message`
ignores harmlessly (it is an `if/elif` chain with no `else`).

**Not a CLI upgrade.** The Claude Code CLI was never touched — it was already
current and was the component *emitting* the message. The fix is entirely on
the Python SDK side.

**Deliberately NOT upgraded to 0.2.x.** The requirements comment flags
breaking changes there (MCP background-connect default, TodoWrite → Task
tools). 0.1.81 is the last 0.1.x release and fixes this bug.

## Fix 2 — Model upgrade

**Symptom.**

```
There's an issue with the selected model (claude-sonnet-4-20250514).
It may not exist or you may not have access to it.
```

**Cause.** `.manager.json` pinned `claude-sonnet-4-20250514`, which is
deprecated (retires 2026-06-15) and not available on this account. This file
is entirely separate from the VSCode extension's model setting, which is why
the extension worked while wrapper-spawned sessions failed.

**Resolution order** (verified in `api/routes/chat.py:_resolve_session_provider`):
`assistant_config.json` → `harness_model.claude` wins **only if non-empty**.
It is `""`, so `.manager.json` was the live source.

**Fix.** Set the model to Opus 5 with the 1M-token context:

```json
{ "model": "claude-opus-5[1m]" }
```

Verified against the CLI before committing:

```sh
claude --model 'claude-opus-5[1m]' -p 'reply with exactly: MODELOK'   # -> MODELOK
```

`install/manager.json` (the template for new installs) was updated in git;
the live `.manager.json` is gitignored and must be edited by hand.

## Apply to the other install

Run each step in `~/assistant`.

### 1. Pull (carries this document + the install template only)

```sh
cd ~/assistant && git pull
```

### 2. Upgrade the SDK — the actual crash fix

```sh
cd ~/assistant
.venv/bin/python -c "import claude_agent_sdk; print(claude_agent_sdk.__version__)"
```

If below `0.1.81`:

```sh
.venv/bin/pip install -U 'claude-agent-sdk>=0.1.81,<0.2'
.venv/bin/python -c "import claude_agent_sdk; print(claude_agent_sdk.__version__)"   # expect 0.1.81
```

### 3. Upgrade the model — gitignored, edit by hand

Check `~/assistant/.manager.json`. If `model` is `claude-sonnet-4-20250514`
(or any retired model), set:

```json
{ "model": "claude-opus-5[1m]" }
```

Then confirm nothing overrides it — in `~/assistant/assistant_config.json`,
`harness_model.claude` must be `""` (empty means inherit; a non-empty value
wins over `.manager.json`).

### 4. Restart the backend

A restart is what actually loads the new SDK — the upgrade has no effect on a
running process.

```sh
cd ~/assistant
context/scripts/run.sh -m uvicorn api.app:create_app --factory --host 0.0.0.0 --port 8765
```

### 5. Confirm

```sh
grep -c 'Unknown message type' logs/api_<newest>.log   # expect 0
```

## Notes on the HotMic install only

These were part of the same debugging session but are **not** being applied to
the personal install. Recorded for reference.

**Browser routing.** With the crash fixed, sessions still had no working
browser route: the `claude-in-chrome` extension returned "Browser extension is
not connected", and `chrome-devtools` MCP was disabled (`enabled_mcps: []`).
Setting `enabled_mcps: ["chrome-devtools"]` in `assistant_config.json` made
browser work function and is what the verification run used. This is a real
tradeoff — the MCP path runs an isolated Chrome per session (no access to
logged-in tabs or cookies; the verification run hit a `/login` page for that
reason), whereas the extension drives the real browser with logins intact but
must be connected in Chrome. The two do not conflict; a theory that one was
blocking the other was checked and disproved.

**OpenAI credits exhausted.** The logs show `429 - You have no credits
remaining`. `assistant_config.json` sets `default_model: "gpt-audio"`, so the
orchestrator's voice path fails independently of everything above — almost
certainly the "Voice relay closed by the backend" message seen in session
history. Requires adding credits; not a code issue.
