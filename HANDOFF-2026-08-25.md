# Handoff — session crash + model fixes (2026-08-25)

Three faults found and fixed on the **HotMic install** (`~/HotMic/assistant`).
This document is the instruction set for applying the same fixes to the
**personal install** (`~/assistant`), which is an independent checkout with
its own `context/`, its own `.venv`, and its own local config.

Most of what matters here is **not** carried by this commit — the two config
files involved are gitignored, and the SDK fix is a `pip` operation. Pulling
alone fixes almost nothing. Work through "Apply to the other install" below.

---

## Fault 1 — Sessions never finished connecting

**Symptom.** New chat sessions hung at "connecting" and never came up.

**Cause.** The backend was launched from inside a VSCode Claude Code
terminal, so it inherited `CLAUDECODE=1`. The bundled `claude` CLI refuses
to start when that variable is present:

```
Error: Claude Code cannot be launched inside another Claude Code session.
```

**Fix.** Start the backend from a plain terminal — one that is not a Claude
Code session:

```sh
context/scripts/run.sh -m uvicorn api.app:create_app --factory --host 0.0.0.0 --port 8765
```

**Not a session-ID conflict.** The check is purely environmental; having the
same session open in the VSCode extension is irrelevant.

**Still unfixed — real bug.** `manager/claude/session.py` (~line 957) builds
the child env by *filtering* `CLAUDECODE` out of a copy of `os.environ`:

```python
env = {k: v for k, v in os.environ.items() if k != "CLAUDECODE"}
```

The SDK then merges `{**os.environ, **options.env}`, so the inherited value
wins and the strip is a no-op. Omitting a key cannot override it — the fix is
to set it explicitly empty (`env["CLAUDECODE"] = ""`) so the merge carries the
override. The same latent issue applies to the `env.pop("CLAUDECODE", None)`
calls in `manager/qwen/session.py` and `manager/gemini/session.py` if they
feed the same merge path. Left unfixed deliberately — it is a code change, not
a config one, and was out of scope for this debugging session.

## Fault 2 — "There's an issue with the selected model"

**Symptom.**

```
There's an issue with the selected model (claude-sonnet-4-20250514).
It may not exist or you may not have access to it.
```

**Cause.** `.manager.json` pinned `claude-sonnet-4-20250514`, which is
deprecated (retires 2026-06-15) and not available on this account. This file
is entirely separate from the VSCode extension's model setting, which is why
the extension worked while wrapper-spawned sessions failed.

**Resolution order** (verified in `api/routes/chat.py:_resolve_session_provider`):
`assistant_config.json` → `harness_model.claude` wins **only if non-empty**.
It is `""`, so `.manager.json` was the live source.

**Fix.** Set the model to Opus 5 with the 1M-token context:

```json
{ "model": "claude-opus-5[1m]" }
```

Verified against the CLI before committing:

```sh
claude --model 'claude-opus-5[1m]' -p 'reply with exactly: MODELOK'   # -> MODELOK
```

## Fault 3 — Sessions crashed on browser work

**Symptom.** Sessions died mid-task; the UI showed a crash. Reported as
"crashes whenever I ask it to do anything with the browser."

**Cause — not the browser.**

```
claude_agent_sdk._errors.MessageParseError: Unknown message type: rate_limit_event
```

The bundled CLI (2.1.240) emits a `rate_limit_event` message as a session
approaches a usage limit. The **installed SDK was 0.1.39**, which has no case
for that type, so `parse_message` fell through to `raise MessageParseError`.
That killed `_receive_loop` (`manager/claude/session.py:653`), and the
dead-session reaper closed the session as `subprocess_crashed`.

**Why it looked browser-specific.** Browser work is token-heavy (screenshots,
DOM snapshots), so it reaches the usage limit fastest. The two crashed
sessions never wrote a JSONL at all — they died before any browser tool ran.
Any sufficiently long session would crash the same way.

**The pin was already correct.** `requirements-claude.txt` has required
`>=0.1.81,<0.2` since 2026-06-18, and its comment already documents the
relevant upstream fix ("0.1.40 made the SDK skip unknown message types").
**The venv had drifted below its own floor.** This is the key point for the
other install: `git pull` does not change an installed package.

**Fix.**

```sh
.venv/bin/pip install -U 'claude-agent-sdk>=0.1.81,<0.2'
```

0.1.81 parses the message into a `RateLimitEvent`, which `_process_message`
ignores harmlessly (it is an `if/elif` chain with no `else`).

**Deliberately NOT upgraded to 0.2.x.** The requirements comment flags
breaking changes there (MCP background-connect default, TodoWrite → Task
tools). 0.1.81 is the last 0.1.x release and fixes this bug.

**Not a CLI upgrade.** The Claude Code CLI was never touched — it was already
current and was the component *emitting* the message. The fix is entirely on
the Python SDK side.

## Fault 4 — No working browser route (surfaced once crashes stopped)

With the crash fixed, sessions still could not reach a browser. Two
independent paths existed and **both** were unavailable:

| Path | State | Notes |
|---|---|---|
| `claude-in-chrome` extension | `chrome_extension: true`, but returned **"Browser extension is not connected"** | Native host process was alive; no browser attached to it |
| `chrome-devtools` MCP | `enabled_mcps: []` — not offered to sessions at all | Config in `.mcp.json` was fine |

**What was changed on the HotMic install** — `assistant_config.json`:

```json
{ "enabled_mcps": ["chrome-devtools"] }
```

This made browser work function and is what the verification run used.

**This is a real tradeoff — decide per install, do not copy blindly.**

- **chrome-devtools MCP** runs `--isolated`, launching a private Chrome per
  session. Works headlessly and needs no extension, but sessions cannot see
  logged-in tabs or cookies (the verification run hit a `/login` page for
  exactly this reason).
- **The extension** drives the real browser with existing logins intact, but
  requires the extension to be connected in Chrome.

With both enabled, an agent may pick either. To force the extension path, set
`enabled_mcps: []` and reconnect the extension.

**The two do not conflict.** Verified `chrome-devtools-mcp --isolated` running
alongside the `--chrome-native-host` process with no contention. An initial
theory that one browser was blocking the other was checked and disproved.

## Apply to the other install (`~/assistant`)

Independent checkout: own `context/`, own `.venv`, own gitignored config. Run
each step there.

### 1. Pull (carries only the template + docs)

```sh
cd ~/assistant && git pull
```

This brings `install/manager.json` and this handoff. It does **not** fix the
running install by itself.

### 2. Fix the SDK — the actual crash fix

```sh
cd ~/assistant
.venv/bin/python -c "import claude_agent_sdk; print(claude_agent_sdk.__version__)"
```

If below `0.1.81`:

```sh
.venv/bin/pip install -U 'claude-agent-sdk>=0.1.81,<0.2'
.venv/bin/python -c "import claude_agent_sdk; print(claude_agent_sdk.__version__)"   # expect 0.1.81
```

### 3. Fix the model — gitignored, must be edited by hand

Check `~/assistant/.manager.json`. If `model` is `claude-sonnet-4-20250514`
(or any retired model), set:

```json
{ "model": "claude-opus-5[1m]" }
```

Then confirm nothing overrides it — in `~/assistant/assistant_config.json`,
`harness_model.claude` must be `""` (empty means inherit; a non-empty value
wins over `.manager.json`).

### 4. Browser route — only if browser work is wanted there

Decide using the Fault 4 tradeoff. For the MCP route, set
`enabled_mcps: ["chrome-devtools"]` in `assistant_config.json` and confirm
`.mcp.json` defines a `chrome-devtools` server. For the extension route,
leave `enabled_mcps: []` and reconnect the extension in Chrome.

### 5. Restart from a NON-Claude-Code terminal

Required — a restart is what actually loads the new SDK, and a Claude Code
terminal will reintroduce Fault 1.

```sh
cd ~/assistant
context/scripts/run.sh -m uvicorn api.app:create_app --factory --host 0.0.0.0 --port 8765
```

### 6. Confirm

```sh
grep -c 'Unknown message type' logs/api_<newest>.log   # expect 0
```

## Quick reference — if sessions start dying again

```sh
# 1. Is it the SDK-drift bug?
grep -c 'Unknown message type' logs/api_<newest>.log
.venv/bin/python -c "import claude_agent_sdk; print(claude_agent_sdk.__version__)"

# 2. Is the backend poisoned by a Claude Code parent env?
#    (check the uvicorn PID itself, not its wrapper shell)
tr '\0' '\n' < /proc/<uvicorn-pid>/environ | grep -E '^CLAUDECODE='
```

`Unknown message type` with an SDK below 0.1.81 → Fault 3. `CLAUDECODE=1` on
the uvicorn process → Fault 1.
